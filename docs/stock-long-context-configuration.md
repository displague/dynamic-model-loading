## Current measured choice: resident attention, 32 host FFNs

The [v0.18 continuing-turn comparison](attention-agent-results.md) qualifies the
v0.17 placement on the original capped conversation: **23.985 seconds** for five
retained turns and **0.623-second mean token-bearing TTFT**, versus33.110s and
0.776s for the fresh whole-layer control. The exact-prompt attention reset takes
172.973s and30.569s mean TTFT. These are now measurements of this layout, not TTFT
borrowed from v0.16. Four of five retained answers hit64 tokens; later histories
differ across layouts. This is a bounded performance result, not task completion.

Use the pinned artifacts and common settings below, with `-ngl 65`,
`--n-cpu-ffn 32`, process `GGML_OP_OFFLOAD_MIN_BATCH=2`, K16/p_min0, capacity18432,
and q8_0 KV for both models. Actual target KV is2448MiB CUDA and actual host model
buffers are CUDA_Host. The new sampled peak is14447.10MiB under the15000MiB cap.
Complete arguments and environment are in each v0.18 raw manifest, generated by
`scripts/attention_agent.py` with condition `attention`. Preserve flash attention
on and the recorded thread, batch, stopping and cache settings; no runtime patch.

The separate v0.17 cold-request result is20.57 native decode steps/s after16K;
v0.18 continuing requests yield13.42 native steps/s and11.88 emitted/request second.
Those workload/metric differences matter. There is no32K, higher-cap or complete
target/draft disk-restart qualification. #27 retains the earlier nine short replay
discrepancies; this release adds no independent replay or identity waiver.

## Historical whole-layer threshold8 configuration

The measured configuration reaches **13.50 native decode steps/s** after a populated
16,384-token prefix. This is **2.83x** the best tested default-threshold draft setting;
whole-request throughput improves **42.1%**, with roughly33s prefill and9.4s decode
for128 emitted IDs. Two prompts and two repeats; all16 long requests agree with
their placement-matched target-only references. Independent replay remains separately
tracked. This is a fixed-placement comparison, not an optimized target-only frontier
or a claim about continuing-agent latency. See [results](verification-offload-results.md).

The exact generated argv and child environment are retained in the v0.15 raw assets.
Use `scripts/verification_offload.py`'s long/offload-k16 command constructor as the
source of command-line settings rather than silently adding server defaults:

| Resource / execution setting | Value |
|---|---|
| Target GPU layers |38 including output (37 transformer layers GPU,27 CPU)|
| Target threads / batch threads |24 /24|
| Draft |fullyGPU; threads8 / batch24|
| Context capacity / populated prefix |18432 /16384 tokens|
| KV for both models |q8_0 K and V|
| Logical batch / microbatch |256 /256|

| Draft maximum / minimum / p_min |16 /0 /0|
| Other |flash attention on, fit off, load-mode none, cache-ram0, no context shift|

The threshold is read during backend startup. Do not set it machine-wide. The harness
clears inherited LLAMA/GGML/CUDA settings, records the replacement values and hashes
every executable/DLL/GGUF before loading. Its measured resource bounds are total
sampled GPU<=15000MiB and available host>=2GiB, including desktop use.

This configuration streams cold target tensors for eligible verification blocks.
It does not select semantic neuron pages.

The [v0.16 continuing-conversation study](continuing-agent-results.md) measured
this threshold8/K16 layout with retained state: five continuing turns take34.67s
versus199.10s with explicit reset, and mean client TTFT falls34.09→0.766s. Some
64-token answers are incomplete and retained/reset outputs are not universally

remain. This is the earlier layout's continuing-turn measurement.

## Persistence boundary

The measured reuse is in-process: keep the server and its target/draft contexts
alive, preserve the exact token prefix, and use `cache_prompt` for appended turns.
The pinned [slot save/restore handlers](https://github.com/ggml-org/llama.cpp/blob/d3146f2b56c2db4711ac8391871c9e529d1946d7/tools/server/server-context.cpp#L2574)
call sequence save/load on `ctx_tgt` only. They do not serialize the separate
`ctx_dft` there. A successful slot restore is therefore not qualification of a
complete target/draft restart, its first-turn latency or resumed acceptance.
Cross-restart persistence remains unmeasured. No restart feature is required by
the continuing-turn fixture.
