# v0.14.0 - Stock drafting raises observed throughput; target identity remains unresolved

Stock llama.cpp with a 0.5B draft at maximum length four emits **18.10 tokens/s**,
versus **8.52** for target-only Qwen2.5-32B-Instruct Q4_K_M: an observed **2.124x**
request-rate ratio. **Every nonbaseline configuration differs from the fixed
target reference on sustained generation**, including target-only placement/thread
controls. This is a measured throughput advantage on differing continuations,
not demonstrated identical-output acceleration.

All **260 scalar-smoke comparisons match** generated IDs and stopping state.
The complete matrix comprises **54 native run groups and 574 requests**: 54
warmups, 26 fixed reference requests and 494 candidate comparisons. All groups
finish; no timed request is replaced after inspection. All full resource traces
pass the frozen sampled limits of 15,000 MiB total device-used and at least 2 GiB
host available. The context capacity is 4,096, but actual sustained prompts are
73–103 tokens and every continuation reaches the 256-token cap with EOS enabled.
This is a short-context pilot, not a long-context or broad agent-quality result.

The target's official five GGUF shards total 19.85 GB. Draft memory competes with
target residency, both KV stores and workspaces under the same resource allowance.
Calibration freezes target GPU layer counts and CPU threads independently for each
draft family; evaluation then compares maximum draft lengths 4/8/16. Each sustained
row contains six prompts in three recorded orders, totaling 4,608 emitted tokens.

Every row also matches all twenty scalar-smoke references. Every nonbaseline row
differs on two to four unique sustained prompts, consistently across the three
repeats: **114 differing observations, representing 38 configuration/prompt
situations**. Repeated target-only execution at the original settings matches all
references. The 1.5B K=4/K=8 difference is small relative to repeat variation; the
IQ2 K=4 aggregate's 0.39% advantage over plain target is not a demonstrated gain.

The matched controls preserve both target placement **and CPU thread setting**.
Their gap from the best measured target-only configuration does not isolate memory
placement alone. The IQ2 draft allocates 9,246.93 MiB of CUDA model storage and
1,024 MiB of CUDA KV, reducing target CUDA model storage from 12,842.65 to
3,550.23 MiB. It accepts longer prefixes but loses the economic advantage through
draft execution and the combined target placement/thread cost. It shares neither
weights nor KV, and is not a formal bound on a shared representation.

The largest sampled device peak is 14,992.77 MiB, only about 7 MiB below the ceiling.
Native allocation logs and 200 ms samples do not prove absence of WDDM eviction or
physical storage reads. All model, KV, compute, host-output and sampled resource
records remain available, including startup and gaps between requests.

## Acceptance and fully charged aggregate costs

Actual final verification events reconcile with native attempted/accepted counters.
The release retains per-request accepted-prefix survival, attempted-length
histograms, residual direct decode and checkpoint-replay records. It does not infer
acceptance from teacher-forced agreement or treat rejected suffixes as free.

At K=4, P(A>=4) is **0.430 / 0.501 / 0.680** for the 0.5B, 1.5B and IQ2 drafts.
At K=16, P(A>=16) is **0.075 / 0.125 / 0.247**. Longer acceptance is useful only
when its cost and memory competition also pay. These curves describe the tested
stock execution paths; the identity failures remain attached to them.

Whole completion-request time is **117.350 ms/emitted token** for target-only and
**55.241 ms/emitted token** for 0.5B K=4. It includes prefill, discarded drafting,
verification and coordination inside the HTTP completion interval. Startup,
template/tokenization, artifact hashing and separate metrics reads are outside.
The detailed report also preserves the protocol's emitted/native-decode metric,
native decode-step rate, prefill, startup, per-prompt paired rates and repeat spread.
Native decode timing excludes the first emitted token; that denominator difference
is explicit. Non-streaming requests do not measure client time to first token.

Dividing request totals by recorded cycles gives an accounting normalization, not
isolated cycle or component latency. For a hypothetical fully charged cycle of C
seconds, beating measured rate R by factor S requires E[N] > S C R. At **400 ms**,
the hurdle is **3.41 emitted tokens** to beat plain target or **7.24** to beat the
fastest observed stock draft; a hypothetical 2x advantage over that draft requires
**14.48**. These are sensitivity calculations, not forecasts or mandatory gates.
No v0.12 reconstructed timing or 1.5B acceptance is imported into this model.

## Rebuilt-prefix agreement does not explain the original differences

The planned first-divergence diagnostic finishes **58 one-token requests in 13
groups**. All **38 baseline/matched/candidate comparisons return the same rebuilt
next token**. However, the rebuilt baseline agrees with its original incremental
decision on only **7/11 unique prefixes**.

The first replay attempt completed those eleven baseline cases, then failed an
exclusive reuse of local port 8099 with WinError 10048 before the next native group
started. A prospective amendment assigned distinct ports and recorded probe
failures. The fresh attempt preserves the same 58-case plan. All **11/11 repeated
baseline tokens and top-ten probability records match exactly**; both attempts
remain archived. No timed benchmark was rerun or changed.

A rebuilt prefix, one-token cap and probability-reporting request do not recreate
the original incremental KV trajectory or verification batch. This result proves
neither harmless numerical drift nor a cache/rollback bug. Top-ten records cannot
reconstruct exact KL. The fixed target reference is retained; no stochastic
distribution-preservation claim follows from this greedy pilot.

## Preserved preparation, failures and validation

Freed storage enabled all eight artifacts, **32,379,130,304 bytes**, to be acquired
and SHA-verified. Thirteen merged artifact-free worktrees were removed with ordinary
Git cleanup, recovering about 530 MB. Checkouts with artifacts or unreadable
directories, restoration copies and original measurements were preserved.

Startup attempts exposed missing allocation verbosity and host pressure under mmap.
Prospective amendments enabled verbosity 4 and stock non-mmap loading, without
relaxing either memory limit. Calibration then produced **41 attempts: 21 complete,
19 resource failures and one separately classified native startup abort**. The
continuation imports the original 39-case ledger byte-for-byte and runs only its
two missing cases; it does not rescore completed calibration. All 63 calibration
requests, failure logs and loading observations are preserved.

The native runtime is llama.cpp **b10919**, source
`d3146f2b56c2db4711ac8391871c9e529d1946d7`, on the Core Ultra 9 275HX / RTX 5080
Laptop GPU, driver 616.64. Measurement source is
`5b4a902b0ccff26c5313aeb5eef7a5a35a46e49a`; the corrected diagnostic uses `1cf1101`.
No code review, CPU tests, downloads or compression ran alongside scored inference.

Publication requires the complete CPU suite on the final clean candidate in the
preserved PyTorch 2.10 and 2.12 environments, mandatory code review, byte-identical
receipt restoration/reanalysis, and verified archive digests. The release validation
asset records actual outcomes and the final commit. CPU tests validate the apparatus;
they do not independently reproduce native inference or resolve the fidelity failure.
