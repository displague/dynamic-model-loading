# v0.17.0 — Keep attention and KV resident; stream host FFNs for verification

Stock tensor placement improves the populated16K result again. With all target
attention/KV on CUDA and32 host-backed FFNs, Qwen2.5-32B-Instruct Q4_K_M reaches
**20.57 native decode steps/s**, versus **15.29** for the fresh whole-layer control.
That is **34.5% more decode throughput** and **15.6% more whole-request throughput**.
Mean128-token request time falls **39.83→34.45s**, including prefill.

The fixed comparison uses two reused16K development prompts and two reversed
repeats. All four paired long outputs match exactly; all eight placement outputs
match the historical references. These observations do not establish universal
numerical identity or agent utility.

| Setting | Whole-layer control | Attention resident /32 host FFNs |
|---|---:|---:|
| Native decode steps/s |15.29|20.57|
| Mean prefill(s) |31.51|28.25|
| Mean complete128-token request(s) |39.83|34.45|
| Peak sampled total GPU(MiB) |13846.39|14534.39|

Both use stock b10919, a Qwen2.5-0.5B-Instruct Q8_0 draft, threshold2, K16,
explicit p_min0, q8_0 target/draft KV, context18432 with16384 populated tokens,
target threads24/24, draft8/24, and batch/microbatch256. The control has ngl38
including output. The candidate has ngl65 plus `--n-cpu-ffn 32`. Total sampled
GPU allowance is15000MiB, with at least2GiB host RAM available. Driver616.92 is
recorded; performance claims use fresh controls rather than attributing historical
differences to this setting. The common resource limit does not mean equal actual
allocations or globally optimized whole-layer residency.

The preceding fixed-K16 threshold sweep selected2: **15.40 steps/s**, versus14.44
at8 and15.13 at4. That is6.7% better decode but only1.0% better complete-request
throughput. All twelve threshold outputs match their historical references.
No new draft, confidence cutoff, adaptive controller or custom runtime was used.

The mechanism evidence confirms actual CUDA_Host allocations, full target KV on
CUDA, and all64 target attention assignments on CUDA in every recorded candidate
graph, with192 FFN projections accounted for. The whole-layer control has37 or64
attention assignments on CUDA depending on the graph. Graph dumps are not executed
operation counts, measured H2D bytes or isolated attention timers; the result does
not validate an assumed180ms CPU-attention residual or an overlap forecast.

Two stops remain visible. The30-host-FFN trial reached15004.39MiB during startup,
crossing the experimental cap by4.39MiB. The original stage stopped without an
allocation decision; this was not physical OOM or a general infeasibility result.
A separately registered fixed32 follow-up then stopped before timing because
JSON serialization changed LF to CRLF and violated the declared byte hash.
The corrected source copies bytes exactly and reruns the entire fixed comparison
in a fresh directory. No old row, hash or bound was waived or replaced.

The evidence covers18 native process attempts and44 inference requests. The
25,305,467-byte raw archive contains2,603 members (239,370,936 uncompressed bytes),
all restored and hash-checked. Analysis from the restored source and raw receipts
reproduces byte-for-byte. Protocol and result reviews are retained. The final
clean candidate requires273 passing tests in each PyTorch2.10.0+cu130 and
2.12.0+cu130 environment before publication; attached receipts identify the exact
commit and tree. Model execution itself uses the pinned native CUDA binary.
